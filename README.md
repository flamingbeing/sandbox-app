# Sandbox app

Made from [app-starter](https://github.com/flamingbeing/app-starter), a template for small offline-first web apps that
are safe from day one. Replace this first paragraph with what the app is once it is filled.

## What you get

- **Worker** (`worker/`): serves `app/` on the app's address, adds security headers (`headers.js`: HSTS, nosniff,
  Referrer-Policy, frame-ancestors, Permissions-Policy, and a Content-Security-Policy that starts as Report-Only),
  answers `/api/claims` (app-devkit `claims.js`, roles from `members.js`) and `/api/csp` (CSP reports, one line each
  in the Worker log: `csp-report.js`), and passes Firebase's sign-in helper pages (`/__/auth/`, `/__/firebase/`) on
  to the project, so sign-in stays on the app's address (those pages get only the framing rule, not the app's CSP).
- **Sample app** (`app/`): a list with add, edit, delete (to the bin), a conflict sheet, a list of saves the server
  refused, a status chip, Google sign-in, sign-out that keeps the device copy (forget wipes it, once nothing is
  unsent), an edit sheet that follows its item, "check for updates" and the version line. Sync is
  [app-sync](https://github.com/flamingbeing/app-sync)'s modules (`createApp` with `auth`, `sync` and `update`, in
  `app/src/cloud.js`), each at an exact version from `core.anawj.com/sync/` named once in `app/index.html`'s import
  map; updates wait for `canReload` (no reload while someone types, a sheet is open or saves are sending).
  Installable, never prompted (`src/boot.js` cancels `beforeinstallprompt`).
- **UI kit** ([decision 0011](docs/decisions/0011-ui-kit-served-from-app-ui.md)): `@core/ui` (sync chip with
  overridable state words `LABELS`, sign-in sheet, conflict sheet, update prompt, refused list) and `@core/theme`
  (custom properties; this device's look (A tinted glass, B colour band, C dense and quiet: [ui-kit.md](https://github.com/flamingbeing/app-ui/blob/main/docs/ui-kit.md),
  [decision 0010](docs/decisions/0010-looks-are-data.md)),
  theme, dark style incl. OLED, style from 8 presets, accent, ground, density and the glass guard;
  palettes worked out from one accent with a contrast floor, applied from `src/boot.js` before the first paint; the
  app's default colour is `APP.accent` in `src/config.js`, `fill.mjs --accent`), with `@core/settings` from
  [app-ui](https://github.com/flamingbeing/app-ui) at the version the import map pins (`core.anawj.com/ui/<version>/`),
  each its own import map entry; the gallery is app-ui's `/kit/`. The screens are one file each in `app/src/screens/`; a new app replaces only those.
- **Files** (a module, `node tools/add.mjs files`; [decision 0009](docs/decisions/0009-files-through-the-worker.md)):
  `@core/files` v0 in `app/public/files/` (own import map entry): `add` keeps a photo or file on the device at once
  (resized, with a thumbnail; date taken read first when `exif` is on), saves its record through sync and uploads it
  through the Worker's `/api/files/` (R2 bucket bound as `FILES`, the same ID token check as `/api/claims`, 100 MB cap)
  when online, with retries; `url` shows it from the device or fetches it; `remove` deletes it. Uploads need the admin
  or member role. The recipe also adds the item sheet's attach buttons, the Worker route, the rules and the R2 binding.
- **Roles**: one role doc per person (`members/{uid}` = `{ role, v }`, roles admin, member, viewer), cached as custom
  claims in the app-devkit rules kit shape, single group `_`. The page asks for new claims at sign-in and whenever
  the role doc's `v` is ahead of its token. Admins change and remove roles through the Worker's `/api/members/<uid>`
  (`worker/members.js`; the page's `members.setRole` and `members.remove`); the rules refuse pages' writes to
  `members/`. A removal also revokes the account: `revoked/{uid}` (rules and files refuse at once), claims cleared,
  refresh tokens ended.
- **Rules** (`app/firestore.app.rules`, built into `app/firestore.rules` with the rules kit's helpers) and their
  emulator tests (`app/test/rules.test.mjs`: the kit's shared cases plus the app's own).
- **Offline from the first visit**: the service worker installs the page, its files, Firebase and the pinned core
  files together (`app/public/sw.js`; its file list is generated by `tools/sw-files.mjs`, never written by hand).
  Firebase is vendored: gstatic's files for the pinned version, served from the app's own address
  (`app/public/vendor/firebase/<version>/`, `tools/vendor-firebase.mjs`).
- **Tests**: Worker, app and tool unit tests; rules in the Firestore emulator; Playwright browser tests (offline save,
  starting with no network, two phones, conflict, sign-out wipe, update reload guard, axe, no CSP reports) against the
  real Worker in Node (`e2e/serve.mjs`) and the emulators (`demo-` project, made-up accounts), on `app/` as it is and
  on a Vite build of it.
- **CI**: Checks (parallel jobs), deploy (Worker) and deploy-rules on app-devkit blocks pinned to an exact version,
  other actions pinned by SHA, `permissions: contents: read` by default, gitleaks, grouped Dependabot, `ubuntu-24.04`.
- **Decisions** in [docs/decisions/](docs/decisions/), numbered; a reversed one is marked superseded, never deleted.

## Start an app

1. On GitHub, "Use this template" (never a fork), then clone the new repo. Go through the
   [new-app checklist](docs/new-app-checklist.md) alongside these steps.
2. Fill it (next section): name, address, design kit, Firebase project.
3. `. tools/dev-setup.sh` (app-devkit into `.devkit/`, `npm ci`, the test environment), then the tests (README,
   "Tests"); all green before the first change.
4. Replace the sample screen (`app/src/app.js`, `app/index.html`) with the app. Keep the wiring in `app/src/cloud.js`
   (one `createApp`, every save through the sync module) and the rules that bite in `AGENTS.md`.
5. An app with photos or files runs `node tools/add.mjs files`, then makes the bucket once before the first deploy:
   `npx wrangler r2 bucket create <name>-files` (the recipe prints this as a NEEDS-YOU line; the deploy fails without it).
6. After adding or removing a file the page loads: `node tools/sw-files.mjs app` (CI fails until the list is current).

## Fill (make it a new app)

```bash
node tools/fill.mjs --name <name> --host <app.example.org> --kit homedesign|nuhs --project <firebase-project-id> \
  [--title "<Title>"] [--web-config sdkconfig.json] [--commit <template sha>]
```

It replaces the template's values (kept in `.starter.json`) in every text file, writes `app/src/config.js` (with the web
app's `apiKey` and `appId` from `firebase apps:sdkconfig WEB` output) and sets `wrangler.jsonc`'s `FIREBASE_PROJECT`.
Running it again changes nothing; `--check` exits 1 when a run would change something. The emulator project becomes
`demo-<name>`; tests never touch the live project.

Then: the Worker secrets `SA_EMAIL` and `SA_KEY` (a service account that may manage Auth users and write Firestore),
the repo secrets for the deploy (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`), the repo variables for the rules
deploy (`FIREBASE_PROJECT`, `WIF_PROVIDER`, `RULES_DEPLOYER`), Google sign-in switched on in the Firebase console, the
app's host as an authorised domain, and a first `members/{uid}` doc with role `admin`.

**Live smoke test**: `.github/workflows/live-smoke.yml` (app-devkit's `live-smoke`) signs a test user in on the
deployed site, by hand and after each Deploy, and runs `e2e-live/signin.live.spec.mjs` (signed in, the list shown, no
console errors). It needs the repo secrets `<NAME>_TEST_EMAIL` and `<NAME>_TEST_PASSWORD` (the name in capitals,
hyphens as `_`; fill renames them) and skips with a notice until they exist. Here the test user has a role, so it sees
the list; the test writes nothing.

`.starter.json` records the template version and commit the app started from; app-devkit's drift report compares an
app with the template and never changes it.

## Tests

```bash
npm ci
node --test 'worker/test/*.test.mjs' 'app/test/*.unit.test.mjs' 'tools/test/*.test.mjs'   # no network
npm run typecheck # app/src under strict, against the pinned app-sync's .d.ts (tsconfig.json)
npm run rules     # rules in the Firestore emulator (needs Java and .devkit/)
npm run e2e       # browser tests (emulators and the e2e server start by themselves)
npm run vite      # Vite build into dist/ (core, Firebase and register.js stay external), its SHELL and stamp
APP_DIR=dist npm run e2e   # the same browser tests on that build
node tools/sw-files.mjs app --check && node tools/vendor-firebase.mjs --check   # the SW list and Firebase (no network)
```

`.devkit/` holds app-devkit's `playwright/`, `rules/`, `tools/` and `worker/` at the pinned version (CI's setup
blocks put it there; locally, `. tools/dev-setup.sh` copies them at the same tag).

`SYNC_DIR=<app-sync checkout> npm run e2e` serves that app-sync build in place of `core.anawj.com/sync/<version>/`:
app-sync's CI runs these tests that way against each candidate (its consumer test) before a release.

## Layout

```text
app/        the app (served at the root of its address): index.html (import map) and
  src/      config.js, cloud.js (wiring), app.js (shell), screen-switch.js, screens/ (one file per screen), dom.js,
            roles.js, boot.js, modules.js (the optional modules' slots), globals.d.ts (types for the check)
  public/   sw.js, app.css, manifest, icons, vendor/firebase/<version>/: served
            as if beside index.html (the Worker looks here on a miss), as Vite's public/ is
worker/     the Worker: sites.js, routes.js, headers.js, members.js, claims.js + custom-token.js (app-devkit copies)
e2e/        browser tests and their server; fixtures/outside-package/ (a page that imports a vendored zod)
tools/      fill.mjs, sw-files.mjs (sw.js's file list), vendor-firebase.mjs (+ firebase.lock.json), stamp-versions.mjs
            (deploy stamp for sw.js), vite-check.mjs (the Vite build check; vite.config.mjs at the root),
            vite-outside-package.mjs (the same for the outside-package fixture), dev-setup.sh (a fresh machine ready
            to test), update-from-starter.mjs (brings newer template commits in; app-sync bumps), add.mjs (modules)
recipes/    one JSON file per optional module (files, search) and the files each brings (README, "Modules")
docs/       decisions
```

## Adding an outside package

An outside ESM package (one with no dependencies of its own) plugs in the way `@core/*` does. The proof is a fixture
page, `e2e/fixtures/outside-package/` (zod 3.23.8); the starter app imports none of it, so a new app carries only what
it adds. An app that does not need the proof deletes that folder, `e2e/outside-package.spec.mjs`, `tools/vite-outside-package.mjs`,
its `&& node tools/vite-outside-package.mjs` in the `vite` script, the `sw-files` line in `checks.yml` and the `zod` and
fixture entries in `tsconfig.json`.

1. **Vendor one file, exact version:** `npm pack <name>@<version>`, copy its single ESM file (and `LICENSE`) to
   `app/public/vendor/<name>/<version>/`, plus its `.d.ts` files. A live CDN would break the offline start.
2. **Name it in the import map** (`app/index.html`): `"<name>": "./vendor/<name>/<version>/<file>.mjs"`.
3. **Types:** a `paths` entry in `tsconfig.json` pointing at the vendored `index.d.ts`, so `npm run typecheck` stays strict.
4. **Offline:** `node tools/sw-files.mjs app` lists the file in `sw.js`'s SHELL (CI runs its `--check`).
5. **Vite:** add `resolve.alias: { <name>: '<the vendored file>' }` to `vite.config.mjs` (an npm dependency of the same
   version works too); `tools/vite-outside-package.mjs` shows the build keeps it out of pages that do not import it.

## Modules

Optional parts come in and go out with one command each, so an app carries only what it uses:

```bash
node tools/add.mjs search                          # the template's recipe at the commit this app was made from
node tools/add.mjs <owner/repo>@<tag|sha>:recipes/<module>.json   # a recipe from another repo (where the module was born)
node tools/add.mjs --remove search                 # takes it out again; a file the app changed is kept and listed
```

The template ships two recipes: `files` (`@core/files`, the Worker route, rules and R2 binding; needs the bucket made
once) and `search` (`@core/search`, operators `field:`, `"phrase"`, `-leave-out`, `OR`, with `insertOperator` and
`usesOperators` for a "?" list). A recipe (`recipes/search.json`; its fields are listed at the top of `tools/add.mjs`) names the module's
import map entries, vendored folders, files, tsconfig `paths` and `include`, Vite source alias, CSS custom
properties, owner steps (printed as NEEDS-YOU lines) and notes. The glue goes into `app/src/modules.js`: one import and
one slot per module (search fills the list's `listFilter` slot; `#list-tools` holds its box). Every edit is idempotent;
re-adding from a newer source merges three-way into files the app changed. Afterwards `sw.js`'s list and the import
map's CSP hash are regenerated, and `.starter.json` `"modules"` records where each module came from. CI's `full` and
`full-vite` jobs add both recipes to a scratch copy and run the whole suite on it; the lean app is tested on its own.

## Update from the template

`node tools/update-from-starter.mjs --dry-run`, then without `--dry-run`: a three-way merge per file from the template
commit in `.starter.json` (the app's values swapped in first; generated files regenerated), never a history rewrite.
`--sync <x.y.z>` bumps app-sync alone; `--behind <n>` fails when the app is more than n commits behind. Details and
the rest of the list: [new-app checklist](docs/new-app-checklist.md), "Staying current with the template".

## Move an app onto 1.0

For an app already made from this template (or on the one-object `createApp` of app-sync 0.8.x), one PR:

1. **Versions, named twice and bumped together:** `app/index.html`'s import map (`@core/app`, `@core/auth`,
   `@core/sync`, `@core/update` at `https://core.anawj.com/sync/<1.x.y>/`) and the `app-sync` devDependency tag in
   `package.json`; then `npm install`, `npm run typecheck`.
2. **Modules:** `createApp({ config: { name, sdk }, modules: [auth(...), sync(...), update(...)] })` in
   `app/src/cloud.js`, as this starter does; the app reads `app.auth`, `app.sync`, `app.update`. Sign-out now keeps
   the phone's copy and unsent saves; another account signing in wipes them, and "forget this device" is the only
   other wipe. Stored formats are unchanged, so phones keep what they hold.
3. **Layout:** static files into `app/public/` (the Worker looks there on a miss, so nothing else moves); code in
   `app/src/`.
4. **Offline list:** copy `tools/sw-files.mjs`, replace the hand-written SHELL in `sw.js` by running it, and add its
   `--check` to CI.
5. **Firebase:** copy `tools/vendor-firebase.mjs`, run `node tools/vendor-firebase.mjs <the version the app pins>`
   (it points the import map at the vendored files), drop `https://www.gstatic.com` from the CSP's `script-src` and
   `connect-src`, and update the import map's hash in `worker/headers.js` (its test prints the new one).
6. Tests green, including a phone that saved offline on the old version (its outbox sends after the update).

## Switch to Vite in one PR

Vite is already here as a check (`vite.config.mjs`, `npm run vite`, CI job "vite" runs the whole browser suite on
the build), so switching is one small PR that changes what is deployed, not the app:

1. `.assetsignore`: add `app`, remove `dist`; `worker/routes.js`: the root folder becomes `dist/` (and `SHARED`, if
   any). `e2e`: set `APP_DIR=dist` for every run (the tests already pass on it).
2. `deploy.yml`: `install: true`, `build-command: npm run vite` (it builds, writes `dist/sw.js`'s list and stamps it),
   and no separate `stamp-command`.
3. Keep the import map: core, Firebase and `register.js` stay external, at the versions the map pins. Bundling core
   from source instead (app-sync's package entries, unused modules shaken out) is a later, separate choice.
4. `index.html` may then move to the repo root and `src/` beside it (Vite's default layout); `vite.config.mjs`'s
   `root` changes with it.

## Refresh from the starter

sandbox-app is the starter's live sample (sandbox-app.flamingbeing.com, Firebase project `sandbox-app-app`). To bring it
up to the starter's main:

```bash
git checkout -b refresh/starter-<sha>
git ls-files -z | xargs -0 rm -f            # clear the old files, keep .git
(cd ../app-starter && git archive HEAD) | tar -x
node tools/fill.mjs --name sandbox-app --host sandbox-app.flamingbeing.com --kit homedesign \
  --project sandbox-app-app --title "Sandbox app" --accent "#3a6390" --commit <sha>
npm ci && node tools/sw-files.mjs app       # then the tests (Tests, above)
```

Save `app/src/config.js` before clearing and copy it back before fill (fill keeps its web config), or pass `--web-config <web.json>` (`firebase apps:sdkconfig WEB`). Open a PR, merge on green; the deploy workflow ships it. A new starter release that adds a Worker binding needs it
created first (the files bucket: `npx wrangler r2 bucket create sandbox-app-files`).
